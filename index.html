模块 01 · 动机

传统网络栈把 CPU 放在了数据路径正中间

一次 4 KB 的 TCP 发送，数据要被内核复制、排队、加锁，再逐层封装；接收端反过来再走一遍。RDMA 把整个协议栈下沉进网卡（HCA / RNIC，Host Channel Adapter / RDMA NIC），CPU 只负责下指令和收结果。

两条路径 · 逐跳对比

内核 TCP

每次发送至少 1 次系统调用、2 次内存拷贝；接收端靠中断唤醒软中断，再唤醒进程。协议处理与数据搬运全部消耗 CPU 周期，且随带宽线性增长。

RDMA

应用在用户态写 WQE（Work Queue Element，工作队列元素）、敲一次 doorbell（门铃寄存器）。网卡自己取数据、组包、重传、写对端内存。远端 CPU 在数据路径上完全不参与，小消息延迟进入微秒级。

要理解后面所有细节，先记住三件事：控制路径（建连、注册内存、配置 QP）可以很慢、可以走内核；数据路径必须极快，所以它在用户态、由硬件执行；完成通知是异步的，网卡把结果写进队列，应用自己来取。

代价是另一套复杂度：内存必须先注册并 pin 住，连接是有状态的，错误处理要自己写，拥塞控制依赖网络配置。这份手册剩下的部分，就是在拆这些代价。

模块 03 · 内存

注册，是为了让网卡绕过 MMU

网卡不懂页表。注册内存时，驱动把这批页 pin 住，把物理地址写进网卡自己的翻译表（MPT / MTT），并发给你两把钥匙：本地用的 lkey（local key，本地键），和可以交给对端的 rkey（remote key，远端键）。

lkey 出现在你本地 WQE 的 scatter/gather 项里，告诉本端网卡“从这块内存读”或“写回这块内存”。rkey 随 RETH / AtomicETH 头一起发到对端，告诉对端网卡“允许你读写我哪一块内存”。权限在注册时一次性写进翻译表，之后每次远端访问都由网卡硬件比对。

注册的代价与页数成正比：一次 ibv_reg_mr 可能要 pin 上万页。所以热路径上反复注册/注销内存是常见的性能杀手，正确做法是启动时注册、长期复用，或用内存窗口与按需分页（ODP）。

模块 04 · 连接状态

QP 状态机：四个状态，一次都跳不过去

新建的 QP 什么都不能做。它必须按 RESET → INIT → RTR → RTS 逐步迁移，每一步只允许设置一组特定的属性；跳步或漏设属性，ibv_modify_qp 直接返回 EINVAL。（INIT = Initialized，RTR = Ready To Receive，RTS = Ready To Send。）

      模块 05 · 服务类型

      选哪种 QP：可靠连接不是唯一答案

      传输服务决定了这个 QP 有没有连接、丢包会不会重传、支持哪些操作。选错的代价要么是内存开销爆炸，要么是数据静默丢失。（RC = Reliable Connection，UC = Unreliable Connection，UD = Unreliable Datagram，RD = Reliable Datagram，XRC = eXtended Reliable Connection，DC = Dynamic Connection。）

      服务连接模型可靠性支持的操作典型用途
      RC一对一可靠有序Send/Recv、Write、Read、Atomic、Write+Imm存储、RPC、MPI、几乎一切
      UC一对一不可靠Send/Recv、Write（无 Read / Atomic）特定 HPC 场景，少见
      UD一对多，无连接不可靠仅 Send/Recv，单包 ≤ PMTU建连前的引导、多播、控制面
      RD可靠数据报可靠同 RC需 EEC，实际几乎被淘汰
      XRC共享接收队列可靠同 RC接收侧 QP 数量成灾的多进程服务
      DC动态连接可靠同 RC（+DCT 号寻址）大规模 GPU 集群，硬件按需建连

      RC 的问题在于 QP 数量按平方增长：N 个节点、每节点 p 个进程要两两通信，就需要 N·p² 个 QP，每个 QP 都占网卡缓存与内存。UD 用一条 QP 发往任意目的（靠 DETH 头里的目的 QPN 寻址），代价是不保证送达、单个消息不能超过 PMTU（Path Maximum Transmission Unit，路径最大传输单元），且接收端必须能从 GRH 里解析来源。

      XRC 让多个进程共享一个接收 QP，DC 则把“建连”这件事交给硬件按需完成——发送时只写 DCT（Dynamic Connection Target，动态连接目标号），不需要对端预先知道谁要来连。这两者都是为规模问题准备的补丁。

      模块 06 · 数据路径

      一次 post_send 的旅程

      从应用写下第一个字节，到 CQ 里出现 CQE，中间只有一次系统调用都没有——全是用户态写内存加一次 MMIO。逐步看这条流水线。

      流水线 · 点击步骤或播放

      第 2 步值得单独说：WQE（Work Queue Element，工作队列元素）是写在你自己的内存里的，SQ 是应用与网卡共享的环形缓冲区，libibverbs 只是替你算好偏移量。所谓 doorbell（门铃），就是对网卡的一个映射到用户空间的寄存器做一次写，告诉它“环上有新条目了”。这就是 kernel bypass 的全部秘密：没有陷入内核，没有拷贝。

      第 6 步是零拷贝的另一半：对端网卡拿着 BTH（Base Transport Header，基础传输头）里的 QPN 找到 QP 上下文，再用 RETH（RDMA Extended Transport Header，RDMA 扩展传输头）里的 rkey 查翻译表，把数据直接 DMA 进你的缓冲区。整个过程中，对端操作系统和 CPU 都不知道这件事发生过。

      模块 07 · 操作语义

      四种操作，差在谁必须参与

      SEND 是对端 CPU 必须参与的双边操作；WRITE、READ、ATOMIC 是单边操作，对端只有网卡在工作。这张差别决定了你的程序要不要在对端跑线程。（下文 WRITE_WITH_IMM 中的 IMM = Immediate，立即数。）

      时序 · 选择操作

      单边操作的诱惑很大——对端不需要 post_recv，不需要唤醒线程，延迟更低。但它要求请求方事先知道远端虚拟地址和 rkey，这通常要先用 SEND/RECV 交换一次元数据。所以真实系统里两者总是配合使用：控制面走 SEND，数据面走 WRITE/READ。

      WRITE_WITH_IMM 是折中：数据单边写入，但会额外带一个 32 位立即数，在对端产生一条 IBV_WC_RECV_RDMA_WITH_IMM 完成事件——相当于“写完了，顺便敲一下门”。这是构建生产者/消费者队列最常用的原语。

      PMTU 决定一个小消息之外的一切

      超过 PMTU 的消息会被网卡切成首包、中间包、尾包，opcode 随之改变。PMTU（Path Maximum Transmission Unit，路径最大传输单元）越大，头部开销越小，但延迟抖动也越大。自己算一遍。

      模块 10 · 可靠性

      PSN、NAK 与 go-back-N

      可靠连接不是魔法：每个报文有 24 位 PSN（Packet Sequence Number，包序号），接收端发现跳号就回 NAK（Negative Acknowledgement，否定确认），发送端从缺的那个序号起重发后面全部。走一遍丢包现场。

      现场重演 · PSN 3 丢失
      AETH syndrome含义触发场景
      0x00ACK（Acknowledgement，确认）正常确认，MSN（Message Sequence Number，消息序号）表示已收到的最新消息序号
      0x01RNR NAK（Receiver Not Ready，接收方未就绪）接收队列没有可用的 RECV WR，等 min_rnr_timer 后重试
      0x60无效请求 / 序号错误PSN 跳号、opcode 与 QP 状态不符
      0x61远端访问错误rkey 无效、权限不足、地址越界
      0x62远端无效 RD 请求不支持的 RDMA READ 组合
      0x63远端操作错误对端内部错误，无法完成请求
      0x64无效 RD 请求RD 服务下的非法请求

      超时重传和 NAK 重传是两套机制。timeout 字段是 4.096 µs × 2n 的本地确认超时，retry_cnt 控制超时重试次数，rnr_retry 控制收到 RNR 后的重试次数（7 表示无限）。三者都设得太小，链路稍有抖动 QP 就进 ERROR，所有未完成的 WR 变成 IBV_WC_WR_FLUSH_ERR。

      要注意 RC 的回退是 go-back-N（回退 N 帧）而不是选择重传：一个包丢了，它之后的包即使已经到达也会被丢弃并重发。这也是为什么在高丢包率环境里，PMTU 太小会显著放大重传流量。

      模块 11 · 拥塞

      无损以太不是免费的

      InfiniBand 用链路级信用保证不丢包；RoCEv2 跑在以太网上，只能靠 PFC（Priority Flow Control，优先级流控）造出“无损”，再用 ECN（Explicit Congestion Notification，显式拥塞通知）+ DCQCN（Data Center Quantized Congestion Notification，数据中心量化拥塞通知）免得这张无损网在拥塞时变成一张堵死的网。

      交换机出口队列 · 拖动看会发生什么 Kmin 30% · Kmax 70% · Pmax 100%
      0Kmin 30%Kmax 70%95%100%

      PFC（802.1Qbb）按优先级发 PAUSE 帧，让上游暂停发送，把“丢包”换成“排队”。它有效，但很脆：一台交换机暂停上游，上游的缓冲区开始堆积，可能再去暂停它的上游，形成反压链；配置成环时甚至会出现 PFC 死锁。所以生产环境通常把 PFC 限制在一个专用优先级上，并且只对 RoCE 流量开启。

      ECN + DCQCN 是端到端的闭环：交换机在队列超过 Kmin 后按概率给报文打 CE（Congestion Experienced，已拥塞）标记；接收端网卡看到 CE，生成 CNP（Congestion Notification Packet，拥塞通知报文）回发给发送端；发送端按 α 比例降速，没有 CNP 时再按定时器慢慢升回来。α 随 CNP 密度增长，避免对单个标记反应过度。

      还有一条更根本的差别：IB 的流控是逐跳信用制，接收方有多少缓冲就发多少信用，永远不会溢出；RoCEv2 的 PFC 是逐跳暂停，只能刹车，不能预约。这就是为什么 RoCE 集群的网络配置比 IB 复杂得多。

      模块 12 · 性能

      小消息看延迟，大消息看带宽

      同一张网卡，64 字节和 4 MB 的性能瓶颈完全不是一回事。下面这张表是排障时最先该看的东西。

      消息规模主导因素观察到的现象该怎么做
      ≤ 256 B延迟 + 消息率（Mpps，Million packets per second，百万包/秒）带宽远低于线速，CPU 单核打满用 inline 发送、减少 WR 数量、多 QP 分散到多核
      1 – 4 KB延迟与每包开销刚好一个 PMTU，效率 98.5%确认 path_mtu=4096；小消息考虑合并
      64 KB在途请求数（window）单 QP 跑不满链路增加 outstanding WR / max_rd_atomic，或多 QP
      ≥ 1 MBPCIe（Peripheral Component Interconnect Express，外设互联总线）与内存带宽多流并发后总带宽不再增长看 PCIe 代际与通道数、NUMA（Non-Uniform Memory Access，非统一内存访问）亲和、DMA 写合并

      调优清单

      • 预注册内存，把 ibv_reg_mr 移出热路径；确需动态缓冲区就用内存窗口或 ODP（On-Demand Paging，按需分页）。
      • 选择性 signaling：只给需要确认的 WR 设 IBV_SEND_SIGNALED，其余靠 CQ 里的批量完成，减少 CQE 与中断。
      • 批量 poll：ibv_poll_cq 一次取 16–32 条；专用轮询核绑核，关掉该核的 C-state 与中断。
      • PMTU 拉到 4096，并确认交换机 MTU 与两端一致；RoCEv2 常配 9000 字节巨型帧。
      • 多 QP 打散：单 QP 受发送窗口限制，多 QP 才能吃满 400G 端口；注意 QP 到核的亲和性。
      • 超时与重试：timeout 按 RTT 量级设置，retry_cnt=7、rnr_retry=7 在调试期更安全。

      用 WRITE_WITH_IMM 拼一条生产者/消费者队列

      单边写入负责搬数据，立即数负责通知。生产者只写自己的内存加一次 doorbell；消费者等的是网卡投递的立即数，而不是去轮询共享内存。整个模型只有一个环缓冲区和一个计数器。（IMM = Immediate，立即数；CQE = Completion Queue Entry，完成队列条目。）

      实验 · 环形缓冲区
      节点 A 生产者

      A 侧只持有一块本地 MR（Memory Region，内存区域）和一个 <remote_addr, rkey> 对。每次生产：

      1. 写 64 字节记录进自己的发送缓冲
      2. 构造 WQE，opcode = WRITE_WITH_IMM
      3. imm_data 里放环槽序号
      4. post_send → doorbell
      已投递0
      窗口占用0 / 3
      线路 单边写入，对端无 WR
      head 0 tail 0 占用 0/8
      空 已写未消费 刚消费
      节点 B 消费者

      B 侧从没 post 过 recv WR。它只在 CQ 上等，拿到的 CQE 带 IBV_WC_RECV_RDMA_WITH_IMM 与 imm_data（立即数）：

      CQ 为空 · polling
      已消费0
      收到的 imm—

      这个设计的精妙处在于通知与数据走同一条路径。普通的 RDMA WRITE 是静默的：数据写进对端内存，对端不会收到任何事件，只能自己轮询一个标志位。加上 IMM 之后，网卡在写完之后额外生成一条 CQE，把 32 位立即数送到消费者的完成队列里——数据到达与通知到达是原子的，不存在“数据还没落盘就收到通知”的窗口。

      环槽序号放在立即数里，而不是放在记录头里，这样消费者不需要读内存就能知道该处理哪个槽。这也是为什么真实系统里 imm_data 总是编码索引、长度或标志位：它是唯一能在不额外读内存的情况下随完成事件一起送达的信息。

      流控是另一半。环形缓冲区的容量是 8，生产者的发送窗口是 3，两者共同决定生产者能跑多快。窗口小于环深度，是为了让“窗口用尽”比“环满”更早发生——这也是真实系统的常态：max_send_wr 通常远小于对端能容纳的消息数，瓶颈在网卡的在途请求表，而不在内存。窗口用尽时，生产者的下一次 post_send 会返回 ENOMEM；环满则需要消费者先取走数据。真实系统里，环满的信号通过反向的 WRITE_WITH_IMM 回传——两个方向各一条 QP，构成完整的信用闭环。

      术语表与动手实验

      最后是查表用的部分。没有 RDMA 网卡也能练：Linux 的 soft-RoCE（rxe）驱动在普通以太网上实现了一套软件 QP，语义与硬件一致，只是慢。

      动手：在自己机器上跑通一条 RC 连接

      • sudo rdma link add rxe0 type rxe netdev eth0 —— 创建软件 RDMA 设备（内核需 CONFIG_RDMA_RXE）。
      • ibv_devices / ibv_devinfo -d rxe0 -v —— 确认设备、GID 表与支持的 QP 类型。
      • ib_write_bw -d rxe0 -s 4096 -n 10000 —— 双边跑一次 WRITE 带宽；换 ib_write_lat 看延迟。
      • ib_send_bw / ib_send_lat —— 对比双边 SEND 与单边 WRITE 的差异，体会接收端 CPU 的作用。
      • 用 tcpdump -i eth0 udp port 4791 -XX 抓一次 RoCEv2，对照第 08 节逐字节读 BTH。
